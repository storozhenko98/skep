BOUNDARIES, NOT BRANDING

Understand what runs where.

Skep is intentionally explicit about the trust boundary. The Mac app orchestrates; the host service owns the privileged runtime; every workspace is a microVM.

01

Your private SSH keys and Google Cloud credentials stay on your Mac.

02

The remote service is reached through SSH and a host-local Unix socket—not a public API port.

03

Host binaries ship with the app, are checksum-verified, and update without deleting workspace state.

04

Every agent gets its own Linux filesystem and Docker daemon instead of sharing development state on your Mac.

QUESTIONS

The short answers.

Does Skep run the coding agent for me?

No. Skep creates and connects you to the isolated Linux machine where your preferred CLI agent runs. Install Codex, Claude Code, OpenCode, or any other terminal-based development tool in your builder, then include it in your reusable template.

Is Skep open source?

Not yet. The current beta is distributed as a binary while the product and release model settle. The underlying Microsandbox runtime is Apache-2.0 software.

Does it replace Docker?

No. Skep creates the isolated Linux machines. Docker runs normally inside each builder and workspace.

Does Skep create cloud VMs?

Not in this preview. Point it at a compatible Linux VM you already control. It can parse a complete gcloud compute ssh … --tunnel-through-iap command for you.

What happens to my data when Skep updates?

The Mac app replaces matching control binaries and restarts the service. Builders, templates, workspace disks, Docker data, and exports remain on the selected host.

Why does the remote VM need KVM?

Skep runs a microVM runtime inside that host. Cloud VMs therefore need nested virtualization enabled and must expose /dev/kvm to the guest.
